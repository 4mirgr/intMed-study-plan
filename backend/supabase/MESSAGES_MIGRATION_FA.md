# مهاجرت پیام‌ها و اعلان بلادرنگ

فایل `messages.sql` یک مدل نرمال‌شده و افزایشی می‌سازد. جدول قدیمی `tickets` در مرحلهٔ
گذار حذف نمی‌شود؛ trigger هر درج یا ویرایش کلاینت قدیمی را به conversation/message تبدیل
می‌کند. بنابراین rollback رابط کاربری یا حضور هم‌زمان نسخه‌های قدیمی باعث از دست رفتن پیام
نمی‌شود.

## ترتیب اجرا

1. از دیتابیس backup بگیرید و `messages.sql` را در staging اجرا کنید.
2. شمار conversationهای دارای `legacy_ticket_id` را با تعداد `tickets` مقایسه کنید.
3. دسترسی دو کاربر آزمایشی و یک مدیر را بررسی کنید: کاربر فقط thread خودش را می‌بیند؛ مدیر
   همه را می‌بیند؛ کاربر نمی‌تواند با `sender_role=admin` پیام بسازد.
4. Realtime فقط روی `intmed_messages` و read cursor فعال می‌شود. payload اعلان را دادهٔ
   معتبر تلقی نکنید و پس از اعلان، سطر را با JWT فعلی دوباره بخوانید.
5. بعد از استقرار نسخهٔ جدید UI و یک دورهٔ سازگاری، write مسیر قدیمی متوقف شود. حذف جدول
   `tickets` یک migration جدا و همراه با backup/rollback خواهد بود، نه بخشی از این فایل.

متدهای `loadConversations`، `sendMessage` و `markConversationRead` در backend مرورگر آماده‌اند،
اما رابط فعلی عمداً تا پایان بررسی staging از `loadTickets` استفاده می‌کند. سوییچ UI باید پس از
تطبیق شمار پیام‌ها و تست badge/read cursor انجام شود.

## مدل خوانده‌شدن

برای هر participant یک سطر در `intmed_conversation_reads` ذخیره می‌شود. شمار unread باید از
پیام‌های بعد از `last_read_at` محاسبه شود؛ badge کلاینت مرجع مجوز نیست. کاربران فقط cursor
خود را می‌نویسند. مدیر نیز با شناسهٔ حساب خودش cursor مستقل دارد.

## نکات امنیتی

- RLS روی هر سه جدول فعال است و access helper به مالک thread یا مدیر تأییدشده محدود است.
- نقش فرستنده از وضعیت سرور استنتاج می‌شود؛ کاربر عادی نمی‌تواند پیام مدیر جعل کند.
- `client_id` برای idempotency ارسال نسخهٔ جدید رزرو شده است.
- نسخهٔ جدید باید پیام را فقط از RPC `send_intmed_message` با UUID تصادفی `request_id`
  ارسال و خوانده‌شدن را فقط با `mark_intmed_conversation_read` ثبت کند؛ جدول‌ها مستقیماً
  قابل نوشتن نیستند و نرخ ارسال نیز در سرور محدود می‌شود.
- پیام‌های legacy با `legacy_part` یکتا mirror می‌شوند و اجرای دوباره migration تکراری نمی‌سازد.
- تا پایان dual-write، منبع نمایش UI همان tickets فعلی است؛ این تصمیم rollout را برگشت‌پذیر
  نگه می‌دارد و از تغییر ناگهانی تجربهٔ کاربران جلوگیری می‌کند.
